# 项目定位、功能评估与演进路线

更新时间：2026-08-21  
评估基线：`8e09087`  
文档性质：项目总评、产品定位与中长期技术路线

## 1. 执行摘要

Airport Control Plane 已经不是节点台账或页面原型，而是一个能够真实纳管节点、执行 SSH 运维、持续探测、发布代理配置并生成订阅的单机控制面 MVP。

当前最准确的产品定位是：

> 面向个人站长和小型运维团队的轻量代理节点控制面，用较低资源成本统一管理节点、用户、协议、发布、业务链路和运行状态。

下一阶段不应继续把项目描述为泛化的“多云控制平台”，也不宜现在就包装成完整的商业机场面板。结合已经实现的入口、落地、中转、探测和发布能力，更合理的中长期定位是：

> 轻量、多区域、双向代理链路与智能路由控制面。

这里的“双向”包括：

- 国际出口链路：用户从本地或区域入口访问境外资源。
- 回国链路：境外用户通过境外入口访问中国大陆允许访问的业务资源。
- 区域互联链路：香港、日本、新加坡、美国、巴西等区域之间按质量或成本选择中转和落地。

系统目前适合小规模、单管理员、单控制面、可信运维环境。修复 P0 问题并完成 SQLite、任务互斥、资源上限和端到端测试之前，不应视为可长期无人值守的公网生产系统。

## 2. 定位判断

### 2.1 当前是什么

当前项目已经具备以下产品特征：

- 有真实节点注册、事实采集和 SSH 接管。
- 有管理链路与业务链路的初步分层。
- 有 AccessUser、ProxyProfile、NodeGroup 和 ConfigRelease 等代理业务对象。
- 有 sing-box 配置生成、校验、下发、重启与失败回滚。
- 有 VLESS、VMess、Reality 和 Hysteria2 的配置及分享能力。
- 有入口节点、落地节点和 relay 中转的路由语义。
- 有周期探测、任务、操作记录、系统用户和系统模板。
- 有订阅、二维码、厂商台账与成本汇总。

因此它已经超出“VPS 资产管理工具”，本质上是代理网络的控制面。

### 2.2 当前不是什么

当前项目还不是：

- 完整的终端用户自助机场面板。
- 多租户 SaaS 控制平台。
- 可横向扩展的高可用控制面。
- 通用 SD-WAN 或通用云资源编排平台。
- 成熟的堡垒机、计费系统或客户关系系统。
- 已完成自动建机、自动替换和弹性扩缩容的云平台。

这些边界需要明确，否则项目会同时向“云管平台、机场面板、堡垒机、监控平台”四个方向扩张，最终每个方向都不够稳定。

### 2.3 推荐的目标定位

建议把产品主线收敛为：

> 以节点纳管和配置发布为基础，以多区域代理链路编排、持续质量探测和智能选路为核心的轻量控制面。

目标用户优先级：

1. 个人站长和小型代理网络运维者。
2. 需要管理多地域 VPS、LXC、NAT 节点的技术团队。
3. 需要建立国际出口、回国访问或区域中转链路的业务运维人员。
4. 后期再考虑终端订阅用户、自助开通和商业计费。

## 4. 已有架构优势

### 4.1 控制面与边缘节点都比较轻

控制面只有 Node.js 和少量依赖，节点侧以 SSH 和一次性脚本为主，符合低配置 VPS、LXC 和 NAT 容器的实际环境。

### 4.2 业务对象已经形成

`Node -> AccessUser -> ProxyProfile -> NodeGroup -> ConfigRelease -> Share` 已经构成可继续演进的业务骨架，不需要推倒重做。

### 4.3 管理链路与业务链路开始分离

项目已经意识到以下两种链路不能混用：

- 管理链路：控制面如何通过 SSH 接管节点。
- 业务链路：终端流量如何进入入口、经过中转并到达落地。

这是后续实现回国链路、国际出口链路和智能路由的重要基础。

### 4.4 发布具备基本安全网

sing-box 发布已经包含 staged config、配置校验、旧配置备份、服务重启和失败回滚。Reality 私钥也以节点本地文件为主，没有直接写入控制面配置。

### 4.5 已为低配环境做部分保护

JSON 已经使用临时文件、`fsync`、原子替换和单文件写队列；Web Shell 有输出截断和空闲清理；探测和任务历史也有数量限制。

## 6. 三类目标链路

### 6.1 国际出口链路

用户口语中常称为“翻墙链路”。从产品和技术模型上，建议统一命名为“国际出口链路”或 `international_egress`。

典型路径：

```text
客户端
  -> 本地或区域入口节点
  -> 可选中转节点
  -> 境外落地节点
  -> 目标互联网服务
```

需要具备：

- TCP、UDP、QUIC 网络协议语义。
- 入口与落地分离部署。
- 单跳及多跳中转。
- Reality、TLS、HY2 等配置发布。
- 分阶段探测：入口、入口到落地、落地到目标网络。
- 根据地域、延迟、丢包、可用率和成本选路。
- 订阅输出必须使用真实公网入口，不得暴露内部落地地址。

### 6.2 回国链路

典型路径：

```text
境外客户端
  -> 境外入口节点
  -> 可选香港、日本或其他区域中转
  -> 中国大陆落地或允许访问的业务网关
  -> 中国大陆业务资源
```

需要补充：

- `route_direction = return_to_china`。
- 境外入口和中国落地的独立健康探测。
- 国内目标集，例如业务域名、IP 段和应用分类。
- 国内 DNS 解析策略和防止错误解析的健康校验。
- 对公网高位端口、NAT、LXC 映射的完整建模。
- 对线路运营商、地域和可达目标的标签管理。
- 入口到落地的 UDP 支持，不能只依赖 HAProxy TCP。
- 目标白名单和访问审计，避免将落地节点变成不受控转发器。

回国链路不是把现有 relay 字段反向使用就能完成。它需要独立的方向、目标集、DNS、网络协议和策略模型。

### 6.3 区域互联链路

区域互联用于在多个入口和落地之间选择中转，例如：

```text
中国大陆 -> 香港入口 -> 日本落地
东南亚 -> 新加坡入口 -> 美国落地
欧洲 -> 美国入口 -> 巴西落地
```

它是智能路由的基础，应先实现稳定的多候选路径和质量评分，再增加自动切换。

## 7. 链路数据模型改造

当前 `Node.networking.access_mode = direct|relay` 只能表达较简单的单级关系。建议逐步引入以下实体。

### 7.1 Endpoint

表示一个可被访问或监听的端点：

```json
{
  "id": "endpoint_xxx",
  "node_id": "node_xxx",
  "purpose": "public_entry",
  "network_protocol": "tcp",
  "public_host": "203.0.113.10",
  "public_port": 38022,
  "listen_host": "10.0.0.41",
  "listen_port": 443,
  "nat_mode": "port_mapping",
  "verification_status": "verified"
}
```

核心原则：公网入口和节点内部监听必须分开。

### 7.2 Link

表示两个端点之间可被探测的网络连接：

```json
{
  "id": "link_xxx",
  "from_endpoint_id": "endpoint_entry",
  "to_endpoint_id": "endpoint_landing",
  "network_protocol": "udp",
  "provider": "manual",
  "enabled": true
}
```

### 7.3 Route

表示一条完整业务路径：

```json
{
  "id": "route_xxx",
  "direction": "international_egress",
  "entry_endpoint_id": "endpoint_entry",
  "hop_endpoint_ids": ["endpoint_relay"],
  "landing_endpoint_id": "endpoint_landing",
  "profile_id": "profile_xxx",
  "status": "active"
}
```

建议方向枚举：

- `international_egress`
- `return_to_china`
- `regional_transit`
- `private_access`

### 7.4 RoutePolicy

表示用户流量应匹配哪类线路：

```json
{
  "id": "policy_xxx",
  "priority": 100,
  "match": {
    "domain_set": "china_services",
    "source_region": "BRA"
  },
  "route_pool_id": "pool_return_to_china",
  "strategy": "quality_first"
}
```

### 7.5 RoutePool

同一业务目标可以有多条候选路线：

- 主线路。
- 备用线路。
- 低成本线路。
- 低延迟线路。
- 维护或隔离线路。

智能路由不应直接在节点之间临时拼接，而应从经过发布和验证的 RoutePool 中选择。

## 8. 智能路由设计

### 8.1 第一阶段：规则路由

先实现确定性规则，不要一开始就做复杂算法：

- 按来源地域选入口。
- 按目标域名集或 IP 集选择国际出口、回国或直连。
- 按协议选择 TCP、UDP 或 QUIC 路线。
- 按用户、套餐或节点组限制可用线路。
- 按优先级选择主线和备用线。

### 8.2 第二阶段：健康路由

将探测结果接入选路：

- 最近成功率。
- TCP 建连时间。
- UDP/QUIC 握手结果。
- SSH 接管耗时仅用于运维，不参与业务网络 RTT 评分。
- 入口到落地的分段延迟和丢包。
- 连续失败次数和恢复稳定时间。

建议使用带滞回的状态机，避免线路在临界值附近频繁切换：

```text
healthy -> suspect -> degraded -> unavailable
unavailable -> recovering -> healthy
```

### 8.3 第三阶段：质量与成本综合路由

可以引入可解释的评分模型：

```text
score =
  availability_weight * availability
  - latency_weight * normalized_latency
  - loss_weight * packet_loss
  - cost_weight * normalized_cost
  - load_weight * utilization
```

要求：

- 每次决策保存输入指标、候选路线、得分和最终选择。
- 支持手工固定线路，自动策略不得覆盖人工锁定。
- 变更前做预检，变更后做业务探测。
- 自动切换必须有冷却时间和最大切换频率。
- 失败后可以回退到上一条已验证线路。

### 8.4 数据面执行方式

控制面只负责生成和发布策略，实际流量转发应由节点侧成熟组件承担：

- sing-box：协议接入、路由规则、DNS 和出站选择。
- HAProxy：仅用于明确的 TCP L4 场景。
- 支持 UDP 的成熟转发组件：用于 HY2、QUIC 和 UDP relay。
- 系统路由或策略路由：只在有清晰回滚方案时使用。

不要让控制面进程直接承载用户数据流量。

## 9. 控制面架构演进

### 9.1 保持三个平面分离

```text
控制平面
  API、资产、用户、策略、发布、任务决策

数据平面
  sing-box、TCP/UDP 转发、DNS、实际用户流量

观测平面
  探测、指标、日志、告警、线路评分
```

### 9.2 近期仍采用单机控制面

低配置服务器上优先使用：

- Node.js 单进程 API。
- SQLite WAL 模式。
- systemd 托管。
- 有界任务队列。
- 文件日志轮转。
- 每日 SQLite 在线备份。

暂时没有必要立即引入 PostgreSQL、Redis、Kafka 或 Kubernetes。

### 9.3 需要拆出的内部边界

建议按以下顺序拆分：

1. HTTP 路由层。
2. 节点和 Endpoint 服务。
3. 任务执行与租约服务。
4. 探测与质量评分服务。
5. Route/RoutePolicy 解析器。
6. 发布计划与发布执行器。
7. 订阅和分享生成器。
8. 数据 repository 和事务层。

## 10. 产品路线图

### P0：稳定性和错误执行防护

- 全局 HTTP 异常边界。
- bootstrap 保留现有 SSH 登录策略。
- SSH host key 信任和变更确认。
- 严格发布成功状态。
- 修复 JSON 备份恢复。
- 输出、下载和并发上限。
- 会话续签和登录限流。

### P1：链路模型升级

目标：准确表达 LXC/NAT、TCP/UDP、入口、落地和多跳关系。

### P2：回国和国际出口链路

目标：两类方向都能创建、发布、探测和生成订阅。

- 国际出口线路模板。
- 回国线路模板。
- 目标域名/IP 集。
- DNS 策略。
- TCP 与 UDP 转发组件适配。
- 分段探测和端到端探测。
- 主备线路与手工切换。

### P3：智能路由

目标：在多条已验证路线之间自动选择和故障切换。

- RoutePolicy 和 RoutePool。
- 规则路由。
- 线路健康状态机。
- 可解释的质量评分。
- 冷却、滞回和切换频率限制。
- 变更审计、预检和自动回滚。
- 成本、流量额度和负载参与选路。

### P4：运营与自动化闭环

目标：从技术控制面演进为可持续运营系统。

- 告警通知和事件中心。
- 节点隔离、退役和密钥撤销。
- 厂商 API 建机与销毁。
- 故障节点自动替换。
- 订阅格式扩展和终端兼容性测试。
- 用户门户、配额、套餐和账务能力。
- 多管理员、RBAC、MFA 和完整审计。

## 11. 测试与验收体系

### 11.1 必须补充的自动化测试

- HTTP 鉴权、畸形输入和公开接口测试。
- Cookie 续签、登录限流和代理头测试。
- 重复 bootstrap 回调和任务并发认领测试。
- 探测与资产修改竞争测试。
- JSON/SQLite 故障注入和恢复测试。
- SSH transport 不得回退本机的安全测试。
- NAT 公网入口到内部监听的路由测试。
- Reality、TLS、HY2 的配置和分享一致性测试。
- TCP、UDP、QUIC 探测语义测试。
- 发布校验、激活、复检和回滚端到端测试。
- 前端错误状态、无效节点、重复提交和币种继承测试。
- 桌面和移动端关键流程浏览器测试。

### 11.2 链路验收标准

每条正式 Route 必须同时满足：

1. 数据模型完整且不存在端口冲突。
2. 所有目标节点已完成发布。
3. 服务配置校验通过。
4. 服务进程处于活动状态。
5. 公网入口可达。
6. 入口到落地链路可达。
7. 端到端业务探测通过。
8. 订阅中的地址和端口与实际入口一致。
9. 回滚版本可用。
10. 探测来源、耗时口径和最后验证时间可追溯。

## 12. 合规与安全边界

跨境网络、代理服务、回国访问和用户数据处理在不同司法辖区可能受到许可、内容访问、日志保留和数据跨境要求约束。产品应提供技术上的访问控制、目标白名单、审计、密钥保护和停用能力，并由部署和运营方确认其使用场景符合当地法律、云厂商政策及上游网络服务条款。

项目设计不应依赖隐藏错误、绕过审计或不可解释的自动决策。智能路由的每次选择和自动切换都应可以被查看、复核和回滚。

## 13. 最终建议

项目方向值得继续，现有代码也具备继续演进的基础，但顺序非常重要：

1. 先阻止错误执行、错误发布和数据覆盖。
2. 再用 Endpoint、Link、Route 重建链路事实。
3. 然后实现回国与国际出口的双向线路。
4. 最后在可靠探测和多候选 RoutePool 上实现智能路由。

不要先继续增加更多协议、页面和自动建机入口。当前最有价值的改造是把“节点、入口、落地、中转、协议、探测、发布和订阅”统一到一份可靠的 Route 事实中。完成这一层后，回国链路、国际出口链路、自动切换和成本选路都会从零散功能变成可持续扩展的系统能力。
